The 6 phases (about 5–6 weeks)
0. Setup: install Python 3.11+, VS Code, Git and Docker, and get a Groq API key. A GNews key is optional.

n8n news fetcher (Week 1): n8n runs in Docker and starts each morning at 6:30.
It reads 3–5 news feeds for each topic:
Tech: TechCrunch, ET Tech
Finance: ET Markets, Moneycontrol, Mint, RBI
Politics: PIB, The Hindu, Indian Express
Each article is cleaned up and filtered by keywords.
The articles are combined and sent to host.docker.internal:8000/ingest, with automatic retries and an error workflow.
Python ingest service (Weeks 2–3), for each article:
Skip it if the same link or a near-identical story (over 0.9 similar) is already stored.
Get the full text with trafilatura.
Pull out people, organisations and places with spaCy.
Write a short summary with Groq.
Split it into chunks of about 400 tokens, embed them with bge-small-en-v1.5 and store them in ChromaDB with category, source and date.
Answer engine answer() (Weeks 3–4):
The LLM works out the topic and time range from the question.
It searches by meaning (Chroma) and by keyword (BM25), then re-ranks the results with bge-reranker-base.
Groq writes the answer and must cite its sources. If the news doesn't cover it, it replies exactly: "I don't have news on that."
Streamlit chat (Week 4): a chat window, a sidebar to pick topics and dates, and source links under each answer. An optional "Today's Briefing" panel runs from a second n8n workflow at 7 AM.
Testing (Week 5): 25 test questions:
15 the news can answer
5 about recent dates ("yesterday", "this week")
5 it shouldn't be able to answer
Score them by hand and with RAGAS, then write a 2-page report.

Packaging (Week 6): README, an architecture diagram, the code on GitHub, and a 10-minute demo script.

The workflow
Schedule (6:30 AM) → Feed List → Read RSS → Filter & Tidy → Send to Python /ingest
Change from your plan: your plan has three RSS branches, each with its own Set and Code node, then a Merge. But one RSS Read node can only read one link, so 3–5 feeds per topic would mean 9–15 RSS nodes. Instead, a Feed List node lists every feed with its topic and source name. One Read RSS node then reads each feed in turn, and one Code node does all the filtering and tidying. You get the same result with 5 nodes instead of about 20, and adding a feed is a one-line edit.

Tidy: cleaning each article
RSS output is messy, with HTML tags, codes like &amp;, tracking links and mixed date formats. The Filter & Tidy node:

Raw RSS field	After tidying
title	HTML tags removed, &amp; turned back into &, extra spaces removed
link / guid → url	tracking bits (utm_*, fbclid, #section) removed, so the same story shows up as the same link
isoDate / pubDate → published	one standard date format (ISO)
contentSnippet → snippet	cleaned and cut to 500 characters
(new) category, source	taken from the Feed List row the article came from
(new) keywords	which topic words matched, which helps when checking the output
Filter: which articles get dropped
Each article goes through these checks in order. The first one it fails removes it:

Broken: no title or link. This also catches feeds that failed to load; Read RSS is set to retry 3 times and then carry on rather than stop the whole run.
Too old: more than 36 hours old.
Drop word: "recipe", "horoscope", "cricket" and similar. Words only count as whole words, with plurals allowed, so "ai" won't match "said".
Off-topic: Finance and Politics articles must contain at least one topic word (RBI, Sensex, Lok Sabha…). Tech articles are only checked against the drop list, because tech feeds are already on-topic.
Duplicate: the same link or the same title already appeared in this run. Spotting the same story told differently by different outlets is left to the Python ingest step (Phase 2).
You can tune all of this in the RULES block at the top of the code. The node also logs a count of how many articles each rule removed, which feeds your daily collection report.
